## 一、什么是智能体

### 1.1 定义

智能体（Agent）是具备「**感知 → 规划 → 行动 → 反思**」闭环能力的 AI 系统。与普通 LLM 对话相比，它多了两样东西：

- **手**：能调用工具（读文件、执行命令、调 API、操作浏览器），真正改变外部世界
- **脑**：能多步规划、观察结果、自我修正，而不是单次"一问一答"

### 1.2 与普通对话、RAG 的区别

| 维度 | 普通 LLM 对话 | RAG | Agent |
|------|-------------|-----|-------|
| 核心能力 | 生成文本 | 检索 + 生成 | 规划 + 调用工具 + 反思 + 行动 |
| 有没有"手" | ❌ 只能说话 | ❌ 只能查资料 | ✅ 能改文件、调 API、操作浏览器 |
| 有没有"脑" | 单次推理 | 单次推理 | 多步循环推理（ReAct 循环） |
| 犯错后能否修正 | ❌ | ❌ | ✅ 观察结果 → 反思 → 重试 |

一句话：**RAG 给模型加"眼睛"（能看资料），Agent 给模型加"手脚和大脑"（能行动、能规划、能自我修正）。**

### 1.3 智能体的四大核心能力

| 能力 | 英文 | 含义 |
|------|------|------|
| 感知 | Perception | 理解环境状态与用户目标 |
| 规划 | Planning | 拆解目标、制定与调整步骤 |
| 行动 | Action | 调用工具改变外部世界 |
| 记忆 | Memory | 短期/工作/长期记忆的存取 |
| 反思 | Reflection | 观察结果、识别错误、修正策略 |

### 1.4 一句话本质

```
Agent = LLM（大脑）
      + 工具（手）
      + 记忆（存储）
      + 规划循环 / ReAct（决策机制）
      + 安全护栏（刹车）
```

### 1.5 智能体的核心架构：ReAct 循环

几乎所有现代 Agent 都跑在这个循环上，只是包装不同：

```
输入：用户目标
   ↓
① 思考(Thought)：LLM 分析当前状态，决定下一步
   ↓
② 行动(Action)：调用一个工具（搜索 / 读文件 / 执行命令）
   ↓
③ 观察(Observe)：拿到工具返回结果
   ↓
④ 反思/判断：目标达成了吗？没达成就回到①
   ↓
输出：最终答案
```

**关键点**：循环次数不是固定的，Agent 自己决定"还要不要继续"。这是它与普通流水线的本质区别——有动态决策能力。

## 二、智能体设计核心决策框架

设计一个智能体，本质上是做七个核心决策。这七个决策决定了产品的天花板和安全性。

### 决策 1：给 Agent 什么"手"（工具设计）

工具是 Agent 的能力边界，这一步决定产品上限。

**工具设计五原则：**

| 原则 | 说明 | 反例 |
|------|------|------|
| 单一职责 | 一个工具只做一件事 | ❌ `process_data`（既查又写又删） |
| 明确的输入输出契约 | 参数和返回值结构化、可预测 | ❌ 返回一段自由文本 |
| 失败可感知 | 失败时必须返回错误信息，而不是静默 | ❌ 空 catch 返回 "ok" |
| 幂等性 | 重复调用不会造成破坏 | ❌ "转账"工具不做幂等保护 |
| 权限分级 | 读工具随便调，写工具要审批 | ❌ 所有工具平权，Agent 能删库 |

**工具描述决定调用准确率**：很多 Agent 调错工具，不是模型不行，而是工具描述写得模糊。工具描述应包含四要素——**什么时候用、参数含义、返回什么、什么时候不能用**。

### 决策 2：给 Agent 多少"记忆"（上下文管理）

这是 Agent 设计里最硬核、最容易翻车的一环，分三层：

| 层次 | 内容 | 存储位置 | 生命周期 |
|------|------|---------|---------|
| 短期记忆 | 本轮对话上下文 | LLM 上下文窗口 | 实时 |
| 工作记忆 | 任务中间状态、待办清单 | 结构化 scratchpad | 单次任务内 |
| 长期记忆 | 用户偏好、历史经验、知识 | 向量库 / 数据库 | 跨会话 |

**核心矛盾**：上下文窗口有限，但长任务会疯狂累积 token。三大解法：

1. **摘要压缩**：对话过长时，用 LLM 把历史压成摘要
2. **结构化工作记忆**：不要把"当前计划、已完成步骤、剩余步骤"全塞进 prompt，用独立 scratchpad 维护，每轮只注入相关部分
3. **记忆检索**：长期记忆用 RAG 方式存储，需要时检索注入（直接复用 RAG 能力）

### 决策 3：让 Agent 怎么"规划"（Planning 策略）

| 策略 | 做法 | 适用场景 | 风险 |
|------|------|---------|------|
| 零规划（直接干） | 每轮直接决定下一步 | 简单、步骤少的任务 | 长任务会跑偏 |
| Plan-then-Execute | 先列完整计划，再逐步执行 | 步骤明确、可预期的任务 | 计划不灵活 |
| ReAct（边走边想） | 每轮观察结果后动态决定 | 探索性、不确定任务 | 易无限循环 |
| Plan-and-Solve | 先列计划，允许中途修改 | 中等复杂任务 | 实现复杂 |
| 树搜索（ToT） | 多方案并行探索，选最优 | 深度推理难题 | 烧 token、成本高 |

**实战建议**：别一上来就上最复杂的树搜索。90% 场景用「**Plan-and-Execute + 允许中途修正**」就够了。控制成本永远是第一位。

### 决策 4：怎么防止 Agent"跑飞"（安全与终止条件）

Agent 最大风险不是"回答错误"，而是**失控**——死循环、乱花钱、乱删文件。

**必须设计四层防线：**

| 防线 | 机制 | 例子 |
|------|------|------|
| 循环上限 | 硬性限制最大步数 | 超过 30 步强制停止并汇报进度 |
| 预算上限 | 限制 token / 调用次数 / 金额 | "单次任务最多花 ¥0.5" |
| 危险操作审批 | 写、删、花钱、发消息 → 人类确认 | "Agent 请求删除 3 个文件，是否同意？" |
| 重复检测 | 连续相同操作 → 中断 | "连续 3 次调用同一工具无进展，停止" |

**终止条件设计原则**：宁可"没做完就停"，也不要"做过头"。停下来的 Agent 还能让用户接手，做过头的 Agent 可能造成不可逆破坏。

### 决策 5：单 Agent 还是多 Agent

| | 单 Agent | 多 Agent |
|------|---------|---------|
| 结构 | 一个 LLM 干所有事 | 多个 Agent 分工协作 |
| 优点 | 简单、好调、成本低 | 各司其职、可并行 |
| 缺点 | 长任务力不从心 | 协调成本高、token 消耗大、易互相干扰 |
| 适用 | MVP、简单任务 | 复杂工作流、需多种专业能力 |

**关键认知**：多 Agent 不是银弹，它引入一堆新问题——怎么通信？谁说了算？一个失败怎么办？**很多"多 Agent 框架"其实用单 Agent + 好的工具设计就能解决。**

**经验法则**：先做单 Agent，调到极限，再考虑拆多 Agent。过早拆分会陷入"编排地狱"。

### 决策 6：怎么评估 Agent 做得好不好

Agent 评估维度比单次问答复杂得多：

| 维度 | 指标 | 怎么测 |
|------|------|--------|
| 任务成功率 | 最终完成目标比例 | 人工标注或 LLM 判断 |
| 效率 | 平均步数、token 消耗、耗时 | 日志统计 |
| 工具调用准确率 | 调对工具 / 参数正确比例 | 日志分析 |
| 安全性 | 越权操作、死循环次数 | 日志审计 |
| 成本 | 单任务平均花费 | 账单统计 |

**核心建议**：建一个「任务基准集」（如 50 个真实任务），每次改 prompt / 工具 / 模型都跑一遍对比。没有基准集的 Agent 优化就是盲人摸象。

### 决策 7：模型选型与成本（分层路由）

不同环节对模型要求完全不同，**不要所有环节都用最贵的模型**：

| 环节 | 能力要求 | 推荐类型 |
|------|---------|---------|
| 规划（脑） | 推理强 | 旗舰模型 |
| 执行（手） | 快、便宜 | 性价比模型 |
| 反思（检查） | 逻辑强 | 旗舰模型 |
| 工具调用 | 指令遵循强 | 中等模型即可 |

**这就是分层路由**：简单步骤用便宜模型，关键决策用强模型。一个高频 Agent 系统，模型选对能省 70% 成本。

## 三、市面成熟产品设计案例分析

> 说明：以下基于本人知识库总结，部分数据（如具体版本号、最新功能）可能滞后，实际落地前建议核对官方文档。

### 3.1 OpenAI GPTs / Assistants API

- **设计思路**：把 Agent 抽象为「**指令(Instructions) + 知识(Knowledge) + 工具(Actions) + 模型(Model)**」四个可配置组件。GPTs 让用户无需写代码即可配置出定制助手。
- **核心架构**：Assistants API 提供 Threads（对话线程）、Tools（Function Calling / Code Interpreter / File Search）、Runs 生命周期管理。核心是**把"状态管理"从模型里剥离出来**——对话历史、工具调用状态都由平台托管。
- **可借鉴点**：
  1. 配置化、低代码是降低 Agent 使用门槛的关键
  2. 状态托管（thread/run 生命周期）让开发者不用自己管理复杂上下文
  3. 工具标准化（Function Calling 成为事实标准）

### 3.2 Anthropic Claude（Computer Use + MCP）

- **设计思路**：Claude 的 Agent 能力体现在两个方向——Computer Use（操作电脑）和 MCP（Model Context Protocol，工具/数据连接的标准化协议）。
- **核心架构**：Computer Use 是「**看屏幕截图 → 决策 → 鼠标键盘操作**」的视觉循环，让 Agent 能操作任何有 GUI 的应用；MCP 则定义了统一的"工具/资源"协议，让 Agent 通过标准接口连接任意数据源和工具，类似 USB-C 之于外设。
- **可借鉴点**：
  1. **"手"要标准化**：MCP 的价值在于协议统一，工具可插拔
  2. **"眼"要视觉化**：截图循环是通用 Agent 操作任意界面的关键
  3. 安全设计极重（权限确认、危险操作拦截）

### 3.3 字节 Coze（扣子）

- **设计思路**：可视化编排 Agent，把智能体拆成「**工作流(Workflow) + 插件(Plugin) + 知识库(Knowledge) + 记忆(Memory) + 触发器(Trigger)**」五大模块，低代码搭建。
- **核心架构**：以"工作流"为核心，节点 = 步骤，连线 = 流转，支持 LLM 节点、代码节点、条件分支、循环。知识库负责 RAG，记忆负责跨会话状态。
- **可借鉴点**：
  1. **工作流编排**让 Agent 行为可预测、可调试
  2. 插件生态是冷启动的放大器
  3. 记忆模块化（长期记忆、变量）是产品级的标配

### 3.4 Dify（开源 LLMOps 平台）

- **设计思路**：Agent 的**完整生命周期管理**——开发、调试、部署、监控。同时支持 Agent 模式（ReAct）和工作流模式（固定流程）。
- **核心架构**：RAG 管道 + Agent + 工作流 + 可观测性（日志、追踪、成本统计）一体。
- **可借鉴点**：
  1. **可观测性**是生产级 Agent 的刚需（每次调用花了多少钱、走了哪些步）
  2. RAG 与 Agent 融合，而非二选一
  3. 调试体验（可视化轨迹）极大降低排错成本

### 3.5 LangGraph（图状态机建模）

- **设计思路**：用**图（状态机）**来建模 Agent——节点 = 步骤，边 = 转移条件，共享状态 = 记忆。
- **核心架构**：支持循环、分支、并行、Checkpoint（断点续跑）、Human-in-the-loop（人工介入）、时间旅行（回溯重放）。
- **可借鉴点**：
  1. **状态机建模**是控制 Agent 复杂流程的正解，比线性 prompt 可控得多
  2. Checkpoint + 回溯让"重跑"和"调试"成为可能
  3. Human-in-the-loop 是安全关键路径的标准做法

### 3.6 Microsoft AutoGen（多 Agent 对话）

- **设计思路**：多个 Agent 通过**对话**协作，角色化（UserProxyAgent 代表用户执行，AssistantAgent 负责推理）。
- **核心架构**：Agent 之间通过消息传递协作，支持群聊式编排。
- **可借鉴点**：
  1. 多 Agent 协作的一种可行模式（消息传递）
  2. **但警惕**：多 Agent 引入通信开销和不可控性，多数场景单 Agent 更优

### 3.7 Manus / Devin（自主 Agent）

- **设计思路**：通用/垂直领域的**长任务自主执行**。把任务分解为多步，在沙箱里写代码、跑脚本、浏览网页。
- **核心架构**：任务规划 + 沙箱隔离执行 + 长时间运行管理（后台执行、进度汇报、随时打断）。
- **可借鉴点**：
  1. **沙箱隔离**是让 Agent 能"放手干"的前提
  2. 长任务需要"后台执行 + 进度可见 + 可打断"的体验设计
  3. 任务分解（Todo 列表可见）让用户建立信任

### 3.8 Cursor / Claude Code（编程 Agent）

- **设计思路**：深度集成到具体工作环境（IDE/终端），工具 = 文件操作 + 终端命令 + 测试执行。
- **核心架构**：工具集精简但强大（read_file / write_file / run_command / search），配合安全审批、上下文自动压缩、代码 diff 展示。
- **可借鉴点**：
  1. **工具集少而精**：编程 Agent 就几个工具，但覆盖了核心工作流
  2. 安全审批（写文件前 diff、危险命令拦截）
  3. 上下文压缩是长会话的关键技术

### 3.9 DSH（DeepSeek Harness，一切皆插件）

- **设计思路**：DeepSeek AI 的开源 agent harness，核心是「**一切皆插件**」，由 vendored 的 **Cordis**（组合运行时）驱动。DSH 的定位是「agent 的底座」——会话、agent 循环、工具、审批、记忆、自升级全部是插件，宿主只提供组合运行时。
- **核心架构**（基于 Cordis 源码）：
  1. **Fiber 六态 + epoch 驱动**：`PENDING → LOADING → ACTIVE → FAILED / UNLOADING → DISPOSED`。关键不是「依赖齐就 apply」，而是 **epoch**（依赖实现的 uid 串）变化自动触发 reload/unload——依赖实现换了，插件自动重载。
  2. **Context 是 Proxy**：`ctx.session` 直接读服务（不是 `ctx.get('session')`），`isolate(name, label)` 做作用域隔离、`intercept(name, config)` 做配置拦截。
  3. **能力缝（capability seam）**：一个能力拆成 Service Definition / Provider / Consumer 三角色，各自独立演化，永不只有一角。
  4. **不可变 Package + 版本指针 + 授权 + 回滚**：更新不覆盖旧版，失败可回滚，看门狗自动停用。
  5. **模块系统（`__DSH_BOOT__`）**：客户端懒加载 CJS bundle + slots 组合。
  6. **自修改**：agent 经工具检查/挂载/升级自己的插件。
- **可借鉴点**：
  1. **把「注册」升级为「带生命周期的组合」**：插件只声明 `inject` 依赖，内核负责时序，`ctx.effect()` 的 disposer 随 fiber 逆序撤销。
  2. **能力缝是包拆分的依据**：会话、agent 循环、审批、压缩、LLM、shell、fs、skill 各自独立成包，而不是塞进一个大 SDK。
  3. **依赖重载自动化**：epoch 驱动的 reload/unload 让「热更新」「插件回滚」成为运行时原语，而非手动状态管理。

### 3.10 成熟产品共性总结

纵观所有成熟产品，它们都做到了这几件事：

| 共性要素 | 说明 |
|---------|------|
| 工具标准化 | 都有统一、可插拔的工具协议（Function Calling / MCP / 插件） |
| 状态/记忆剥离 | 上下文和状态由平台托管，不塞进单次 prompt |
| 流程可编排/可建模 | 工作流或图状态机，让 Agent 行为可控可预测 |
| 安全护栏 | 权限分级、危险操作审批、预算/循环上限是标配 |
| 可观测性 | 日志、轨迹、成本统计，生产级必备 |
| 知识库（RAG） | 几乎都与 RAG 融合，提供私有知识能力 |

### 3.10 业界三大权威设计框架（联网获取，2026-08 核实）

> 以下内容通过联网检索三大权威来源获得，是对上述产品案例的"理论升华"，也是本领域公认的设计圣经。

#### 3.10.1 Anthropic《Building Effective Agents》（2024-12）

**核心区分：Workflow vs Agent**

| | Workflow（工作流） | Agent（智能体） |
|------|------|------|
| 编排方式 | LLM 和工具通过**预定义代码路径**编排 | LLM **动态指导**自己的流程和工具使用 |
| 可控性 | 高、可预测 | 低、灵活 |
| 成本/延迟 | 低 | 高（换取更好的任务表现） |
| 适用 | 任务定义清晰、步骤固定 | 开放性问题、步骤数无法预测 |

**一句话**：能用简单方案就别上 Agent。很多"Agent 产品"本质是 Workflow，这没毛病。

**基础构建块：增强型 LLM（Augmented LLM）**

Agent 系统的最小单元 = LLM + 增强能力（检索 Retrieval、工具 Tools、记忆 Memory）。模型能主动生成搜索 query、选择工具、决定保留什么信息。

**五种可组合的工作流模式**：

| 模式 | 做法 | 适用场景 | 典型例子 |
|------|------|---------|---------|
| ① Prompt Chaining（提示链） | 任务拆成顺序步骤，每步处理上一步输出，可加程序化检查（gate） | 任务能干净拆成固定子任务 | 先写大纲→审核→再写正文 |
| ② Routing（路由） | 分类输入，分发到专门的下游任务 | 有明确类别、需分开处理 | 客服问题分流；简单问题用便宜模型、难题用强模型 |
| ③ Parallelization（并行化） | 同时跑多个 LLM 再聚合 | 可并行加速，或需多视角 | Sectioning（分区）+ Voting（投票） |
| ④ Orchestrator-workers（编排-工人） | 中央 LLM 动态拆任务、分派给 worker、汇总结果 | 子任务无法预测（如改多少文件） | 多文件编码任务 |
| ⑤ Evaluator-optimizer（评估-优化） | 一个 LLM 生成，另一个评估反馈循环 | 有清晰评估标准、迭代可带来可衡量提升 | 文学翻译、多轮搜索 |

**自主 Agent（Autonomous Agent）**：用于开放性问题，难以预测步数、无法硬编码路径。成本更高、错误可能复合放大，**必须在沙箱环境充分测试 + 配好护栏**。

**三条核心原则**：
1. **保持简单**（Maintain simplicity）：从简单 prompt 开始，用评估优化，简单方案不够用了再加多步
2. **优先透明**（Prioritize transparency）：显式展示 Agent 的规划步骤
3. **精心打造 ACI**（Agent-Computer Interface）：像重视 HCI 一样重视工具文档与测试

**工具 Prompt 工程（附录核心）**：
- 给模型足够 token 在"写死自己"之前先思考
- 工具格式尽量贴近模型在互联网上自然见过的文本（如 diff 比整文件重写难写、JSON 里的转义是额外负担）
- 避免"格式开销"（如让模型精确数千行、字符串转义）
- **站在模型的视角**：工具描述含示例用法、边界情况、输入格式要求、与其他工具的清晰边界
- **Poka-yoke（防错设计）**：把参数设计得"更难犯错"。Anthropic 做 SWE-bench 时花在工具优化上的时间比 prompt 还多——比如把相对路径改成强制绝对路径后，模型就几乎不再出错

#### 3.10.2 Google《Agents》白皮书（2024-2025）

**核心论点：模型 ≠ 智能体**。智能体 = 模型 + 工具 + 编排层（Orchestration Layer）。

**编排层（认知架构的核心）**：负责维护记忆、状态、推理和规划，执行循环：

```
接收输入 → 规划下一步 → 执行（工具/API/代码） → 观察结果更新状态 → 重复直到完成或满足终止条件
```

**工具三分类**：

| 类别 | 说明 |
|------|------|
| Extensions（扩展） | 第一方 API，与 Agent 深度集成 |
| Functions（函数） | 开发者自定义、暴露给模型的能力 |
| Data Stores（数据存储） | 检索系统（RAG），提供动态上下文 |

**关键洞察**：工具描述是一种 **in-context learning（上下文学习）**——模型靠工具的名称、描述、参数 schema 来决定何时及如何调用。

**三类认知架构**：

| 类型 | 特征 |
|------|------|
| Reactive（反应式） | 简单刺激-响应，无规划 |
| Deliberative（审慎式） | 行动前显式规划 |
| Reflective（反思式） | 执行中自我监控、调整策略 |

**核心结论**：构建有效 Agent 要"超越模型"思考——**编排层和工具接口与模型本身同等重要，甚至更值得投入优化**。

#### 3.10.3 OpenAI Agents SDK（2026 年初发布）

定位：轻量级多 Agent 框架，像写普通 Python 一样定义 Agent，显式声明 handoffs，框架处理路由。

**四个核心原语**：

| 原语 | 作用 |
|------|------|
| Agent | 定义单个 Agent：名称、指令（system prompt）、工具、handoffs |
| Tool | Agent 可调用的函数 |
| Handoff（交接） | 把控制权转给另一个 Agent，第一个停、第二个带完整上下文接管 |
| Guardrail（护栏） | 处理前校验输入 / 发送前校验输出，可 block 或 transform |

**典型模式：Triage（分诊）+ Handoff**——一个路由 Agent 读入消息，交接给若干专家 Agent（Support / Billing / Technical），路由 Agent 自己不作答。

**Guardrail 双护栏**：
- 输入护栏：拦截 off-topic / 有害输入（tripwire 触发即阻断）
- 输出护栏：拦截含 PII（邮箱/手机/卡号）的输出

**内置 Tracing**：每次 run 自动生成 trace（哪个 Agent 处理、哪些工具调用、handoff 路径、每步耗时），可导出到 OpenTelemetry。

**框架选型建议**：

| 场景 | 首选 |
|------|------|
| 多 Agent 路由/交接 | OpenAI Agents SDK |
| 复杂图 + 条件逻辑 | LangGraph |
| 类型安全单 Agent + 类型化输出 | Pydantic AI |
| 完全掌控、无抽象开销 | 原生 SDK |

## 四、工程经验总结与避坑指南

### 4.1 设计原则（十条）

1. **先单后多**：先做单 Agent，调到极限再考虑多 Agent
2. **工具少而精**：3-8 个精心设计的工具，远胜 30 个粗糙工具
3. **状态外置**：计划、进度、中间结果放 scratchpad，不塞进 prompt
4. **安全优先于聪明**：让 Agent"做错事的代价足够小"，比让它更聪明更重要
5. **宁可停，不可过**：终止条件宁可保守，不可激进
6. **成本可控**：分层路由，简单步骤用便宜模型
7. **可观测可回放**：每一步都可追溯，出问题能定位
8. **有基准集**：量化好坏，不做盲人摸象的优化
9. **渐进式放手**：先人工审批，稳定后再自动
10. **体验优先**：进度可见、可打断、可接管，用户信任是 Agent 的命门

### 4.2 常见失败模式（反模式）

| 反模式 | 后果 |
|--------|------|
| 工具描述模糊 | 调用准确率暴跌，Agent 乱用工具 |
| 把所有状态塞进 prompt | 上下文爆炸、成本失控、注意力漂移 |
| 无循环上限 | 死循环烧钱 |
| 无危险操作审批 | 误删数据、误发消息（经典事故） |
| 空 catch 吞异常 | 失败静默，Agent 误以为成功继续跑 |
| 过早拆多 Agent | 编排地狱，通信混乱，成本翻倍 |
| 所有环节用最贵模型 | 成本是必要成本的 3-10 倍 |
| 无基准集直接调 prompt | 优化靠猜，越调越差 |

### 4.3 我的核心经验（Top 5）

1. **Agent 的价值不在"多聪明"，而在"做错事的代价足够小"**。见过一个 AI 运维助手因无审批机制执行了 `rm -rf` 删掉生产数据——工具设计和安全护栏远比模型能力重要。

2. **工具描述是隐形的 Prompt**。很多"模型不行"的问题，本质是工具描述写得模糊。把工具描述当作文档来写，调用准确率能提升一大截。

3. **状态管理决定 Agent 能走多远**。长任务的上下文爆炸是最大技术障碍，摘要压缩 + 结构化 scratchpad + 长期记忆 RAG 三者缺一不可。

4. **模型选型是成本杠杆**。规划/反思用旗舰，执行/工具调用用性价比模型，分层路由能省 70% 成本。这直接接得上大模型价格对比（如 DeepSeek V4 Flash cache hit ¥0.02 的极端性价比）。

5. **用户信任是 Agent 产品的命门**。进度可见、可打断、可接管、可回放，这四个"可"字做到，用户才敢把任务交给 Agent。

### 4.4 业界权威共识（本次联网核实）

综合 Anthropic、Google、OpenAI 三大来源，可以提炼出以下**跨厂商一致的设计共识**，这些是被反复验证的"底层规律"：

1. **简单优先是最高原则**。三家几乎异口同声：先试最简单方案（单个 LLM 调用 + 检索），不行再加 workflow，再不行才上 autonomous agent。Anthropic 原话："成功不是建最复杂的系统，而是建最适合你需求的系统。"

2. **编排层/工具接口与模型同等重要**。Google 明确说"投入优化编排层和工具接口，往往比换更强的模型更有效"；Anthropic 在 SWE-bench 上花在工具优化上的时间超过了 prompt。

3. **工具描述 = 隐形的 prompt = 上下文学习**。三家都强调工具文档质量直接决定调用准确率。要把工具当"给初级工程师写的 docstring"来写。

4. **状态/上下文要外置**。Google 的编排层管记忆状态、OpenAI 的 handoff 带完整上下文交接、Anthropic 的 augmented LLM 把记忆作为独立增强能力——都在避免把状态塞进单次 prompt。

5. **安全护栏是标配而非可选项**。OpenAI 的 guardrail、Anthropic 的沙箱测试+护栏、Google 的终止条件——三家都把"限制 Agent 犯错代价"放在核心位置。

6. **可观测性是生产级门槛**。OpenAI 内置 Tracing、Dify 的可观测性、LangGraph 的 Checkpoint——trace/回放/审计是规模化运营的刚需。

7. **Workflow 与 Agent 是光谱而非二分**。不是"要么 workflow 要么 agent"，而是从确定性到自主性的连续谱，按任务的可预测程度选择合适的位置。

## 五、可复用的设计模板与清单

### 5.1 智能体设计自查清单（十问）

```
□ 1. 目标用户是谁？解决什么具体问题？
□ 2. 需要哪些工具？（列清单，每个单一职责）
□ 3. 每个工具的输入输出契约定义清楚了吗？
□ 4. 上下文管理策略定了吗？（短期/工作/长期记忆）
□ 5. 用什么规划策略？（默认 Plan-and-Execute）
□ 6. 循环上限和预算上限设了吗？
□ 7. 哪些操作需要人类审批？
□ 8. 单 Agent 还是多 Agent？（默认单 Agent）
□ 9. 评估基准集建了吗？
□ 10. 每个环节用什么模型？（分层路由）
```

### 5.2 通用架构模板

```
┌─────────────────────────────────────────────┐
│                用户输入 / 目标                │
└──────────────────┬──────────────────────────┘
                   ↓
        ┌────────────────────┐
        │  规划器 (Planner)   │ ← 旗舰模型，拆解任务
        └────────┬───────────┘
                 ↓
        ┌────────────────────┐
        │  执行器 (Executor)  │ ← 性价比模型，调用工具
        │  · 工具1 工具2 ...  │
        └────────┬───────────┘
                 ↓
        ┌────────────────────┐
        │  反思器 (Reflector) │ ← 旗舰模型，判断是否达标
        └────────┬───────────┘
                 ↓ (未达标则回到规划器)
        ┌────────────────────┐
        │  记忆层 (Memory)    │ ← scratchpad + 长期记忆(RAG)
        └────────────────────┘
        ┌────────────────────┐
        │  安全护栏 (Guard)   │ ← 循环/预算上限 + 审批
        └────────────────────┘
```

### 5.3 工具描述模板

```
工具名：search_documents
用途：在知识库中搜索相关文档（当需要查询资料时使用）
参数：
  - query (string, 必填)：搜索关键词
  - top_k (int, 可选, 默认5)：返回结果数量
返回：JSON 数组，每项包含 title / content / score
不应使用的情况：当用户问题与知识库无关时，不要调用
```

### 5.4 系统 Prompt 模板（骨架）

```
你是 [角色定位]，目标是为用户完成 [具体任务]。

【可用工具】
[工具列表及使用说明]

【工作方式】
1. 先规划：将任务拆解为步骤
2. 逐步执行：每步调用合适的工具
3. 观察结果：根据工具返回判断是否继续
4. 反思修正：出错时调整策略

【安全约束】
- 写/删/花钱等操作必须先征得用户同意
- 连续失败 [N] 次后停止并报告
- 单次任务最多 [M] 步

【输出要求】
- 引用工具结果时标注来源
- 不确定时明确说明，不编造
```

## 六、设计路线图建议

### 阶段一：MVP（1-2 周）
- 单 Agent + 3-5 个核心工具
- 简单的 Plan-and-Execute
- 只做最小安全护栏（循环上限 + 读/写分级）
- 目标：验证"用户真的需要这个 Agent 吗"

### 阶段二：迭代（2-4 周）
- 补充工作记忆 scratchpad 和摘要压缩
- 建立评估基准集，量化优化
- 接入 RAG 长期记忆
- 模型分层路由降成本
- 目标：把任务成功率从 60% 拉到 85%+

### 阶段三：规模化（1-3 月）
- 完善安全护栏（预算上限、审批流、可观测性）
- 按需评估是否拆多 Agent
- 可回放、可审计、可监控
- 目标：稳定、安全、可运营地对外服务
